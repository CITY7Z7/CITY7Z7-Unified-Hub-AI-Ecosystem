# ADR-001: Выбор целевой архитектуры объединения ToolHub и Lab

> **Статус:** Принято  
> **Дата:** Октябрь 2026  
> **Контекст:** Интеграция репозиториев `Talos-popcorn/toolhub` и `Talos-popcorn/lab` в единую поддерживаемую Full Stack систему.

---

## Контекст и проблематика

Исторически проекты развивались параллельно:
- `toolhub` спроектирован как monorepo на базе Bun/npm workspaces (`apps/api`, `apps/admin`, `SDK/JS`), запускающий Fastify сервер на порту 3001 и предоставляющий Swagger UI и панель администратора по префиксу `/admin/`.
- `lab` спроектирован как независимый статический клиент на React 19 + Vite, предназначенный для локального запуска или деплоя на Cloudflare Pages, со встроенным клиентом `HubSDK` для подключения к ToolHub.

При этом:
1. `lab` не имеет собственного бэкенда — он полностью полагается на внешние LLM-эндпоинты и локальное хранилище IndexedDB (Dexie).
2. `toolhub` уже имел функционал статической раздачи SPA панели администратора по префиксу `/admin/` из `apps/admin/dist`.
3. Код клиентской библиотеки `HubSDK` (`toolhub/SDK/JS/sdk.ts` и `lab/src/lib/toolhubSdk.ts`) идентичен побайтово (md5 хеш совпадает).

Перед нами стояла задача выбрать целевую форму объединённого проекта.

---

## Рассмотренные варианты

### Вариант 1: Полный монолит (Merge в единый бандл одного фронтенда)
Попытка слить интерфейс Lab и интерфейс ToolHub Admin в одно React-приложение с одним общим `vite.config.ts`.
- **Преимущества:** Единый процесс Vite, одна точка входа UI.
- **Недостатки и риски:**
  - Разрушение модульности: код админки и код чат-студии имеют разные зоны ответственности и разные сценарии использования (Lab — потребитель навыков; Admin — инструмент инженера по созданию и тестированию навыков).
  - Конфликт зависимостей: в Lab используются тяжёлые библиотеки (Monaco Editor, KaTeX, Tiktoken, Gemini tokenizer, Dexie), которые не нужны в легковесной админке.
  - Высокий риск регрессий в роутинге (`react-router-dom` в Admin vs компонентно-переключаемый интерфейс в Lab).

### Вариант 2: Два независимых процесса с параллельным запуском (Dual Server)
Оставить структуру как есть, упаковав оба проекта в монорепозиторий без интеграции на уровне сервера.
- **Преимущества:** Минимальные изменения в кодовой базе.
- **Недостатки и риски:**
  - Пользователю требуется запускать два или три разных сервера (API на 3001, Admin на 5173, Lab на 5174).
  - Проблемы с CORS и сетевой маршрутизацией при смене портов или удалённом хостинге.
  - Противоречит требованию создания *единой самостоятельной системы*.

### Вариант 3: Монорепозиторий с унифицированным Full Stack сервером (ВЫБРАННЫЙ ВАРИАНТ)
Структурировать проект как модульный Monorepo с единым сервером на базе Fastify:
- `apps/api`: Full Stack бэкенд, обслуживающий:
  - Корень `/` -> раздача клиентского SPA воркбенча Lab (`dist/client`).
  - Префикс `/admin/*` -> раздача SPA админ-панели ToolHub Admin (`dist/admin`).
  - Эндпоинты `/*`, `/prompt`, `/admin/api/*` -> API хаба.
  - `/docs` -> Swagger UI.
- `apps/lab`: Рабочий стол пользователя (AI Studio).
- `apps/admin`: Панель управления и разработки навыков.
- `packages/sdk`: Единая разделяемая библиотека HubSDK для Lab и внешних агентов.
- Корневые скрипты `bun run dev`, `bun run build`, `bun run start` управляют всеми частями системы как единым целым.

---

## Обоснование решения

Вариант 3 признан наилучшим, так как:
1. **Сохраняет 100% исходного поведения:** Ни одна строка бизнес-логики Lab или ToolHub не переписывается принудительно.
2. **Единый порт и отсутствие CORS:** И Lab, и Admin, и API работают на одном хосте и порту (по умолчанию 3000). Запросы из Lab в ToolHub выполняются по относительным путям без межсайтовых ограничений браузера.
3. **Естественное разделение прав:** Обычный пользователь работает в Lab на `/`; инженер или администратор переходит на `/admin/`, вводит мастер-пароль и настраивает раннеры и тулы.
4. **Удобство разработки:** В режиме разработки можно запускать как единый комплекс, так и отдельные приложения независимо.

---

## Последствия

1. Корневой `package.json` настраивается на Bun/npm workspaces: `["apps/*", "packages/*"]`.
2. В `apps/api/src/index.ts` добавляется регистрация статики Lab по корню `/` при наличии сборки `apps/lab/dist`.
3. В `useChatStore.ts` адрес подключения к ToolHub по умолчанию использует текущий хост (fallback на `window.location.origin`), сохраняя возможность ручной настройки на удалённый узел.
4. Общие утилиты и SDK выносятся в единый источник истины.
